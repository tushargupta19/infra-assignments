## Summary

Implements a Kubernetes-deployed configuration service in Go, backed by
PostgreSQL, with database and namespace infrastructure provisioned by
Terraform and the application deployed via plain Kubernetes manifests to a
local `kind` cluster. Includes idempotent schema management, readiness vs.
liveness probes wired to real DB connectivity, structured JSON logging,
graceful shutdown, full local automation (`Makefile`), and an end-to-end
smoke test.

## Infrastructure Design

- **Cluster choice**: `kind` (Kubernetes-in-Docker) — fast startup, minimal
  host footprint (only needs Docker), and portable to CI if this were
  automated further.
- **Database provisioning approach**: PostgreSQL runs as a Kubernetes
  `StatefulSet` with a `PersistentVolumeClaim`, provisioned entirely by
  Terraform (`infra/terraform/postgres.tf`) using the `kubernetes` provider
  against the local `kind` cluster's kubeconfig context. Credentials are
  generated by Terraform (`random_password`) rather than hand-typed.
- **Deployment strategy**: Terraform owns "infrastructure" (namespace,
  PostgreSQL, credentials/secrets); plain Kubernetes manifests
  (`kubectl apply -f k8s/`) own the application (ConfigMap, Deployment,
  Service). Terraform must run first since the app Deployment references a
  Secret and namespace Terraform creates. This split keeps the
  edit-code/redeploy loop fast (no Terraform plan/apply needed for app code
  changes) while still giving the database a proper provisioning story with
  plan/apply visibility.
- **Networking/service exposure**: both app and Postgres use `ClusterIP`
  Services. The app is reached from the host via `kubectl port-forward`
  (`make port-forward` / `make smoke-test`), sufficient for local
  validation. Postgres is intentionally not exposed outside the cluster.

## Configuration and Secret Handling

- Non-sensitive config (`APP_PORT`, `LOG_LEVEL`) lives in a ConfigMap. The
  only sensitive value, `DATABASE_URL` (a full Postgres DSN including
  password), lives in a Secret that Terraform generates and writes
  directly — the app never needs to know the raw DB username/password.
- `DATABASE_URL` is referenced with `optional: true` so the app pod can
  still start (via an in-memory repository fallback) if Terraform hasn't
  been applied yet, avoiding a crash-loop during iterative local setup.
- **What I'd change for production**: use a managed secret backend (Key
  Vault / Secrets Manager / Vault via the CSI Secrets Store driver) instead
  of plain Kubernetes Secrets, require TLS between app and DB
  (`sslmode=require`/`verify-full` instead of `disable`), rotate
  credentials, and stop auto-generating a "production" password via a local
  Terraform run.

## Operational Readiness

- **Health checks**: `/ping` (liveness — process alive, never touches the
  DB) is separated from `/readyz` (readiness — checks DB connectivity via
  `Repository.Ping`). This means a DB outage removes the pod from Service
  endpoints (no traffic routed) without killing/restarting an otherwise
  healthy process.
- **Rollout/restart considerations**: schema migration and Terraform/`kubectl
  apply` are all idempotent, so `make up` is safe to re-run from any partial
  state. Graceful shutdown (`SIGTERM` → `http.Server.Shutdown` with a 10s
  drain) avoids dropping in-flight requests during rollouts.
- **Observability**: structured JSON logs (`log/slog`) including
  DB-connect retry attempts, active repository backend, and shutdown
  events — diagnosable purely from `kubectl logs`.
- **Failure handling assumptions**: startup retries DB connection with
  exponential backoff (10 attempts, capped at 10s) before failing hard;
  at runtime, DB errors surface as 500s with generic bodies (real errors are
  logged, not leaked) and flip `/readyz` to unhealthy.

## Repository Structure

- `cmd/`, `internal/{handler,service,repository,domain}/` — standard Go
  layering; each package is independently testable.
- `infra/terraform/` — split by concern (`main.tf` providers,
  `variables.tf`, `namespace.tf`, `postgres.tf`, `outputs.tf`) so a reviewer
  can find "how is Postgres configured" without wading through provider
  boilerplate.
- `k8s/` — one manifest per Kubernetes object, kept minimal since only the
  application layer lives here (DB manifests live in Terraform instead).
- `Makefile` + `scripts/smoke-test.sh` — single, explicit automation
  entrypoint; no tribal knowledge of command ordering required.

This layout is maintainable because application code, infrastructure code,
deployment manifests, and automation can each be reasoned about
independently, and the Terraform/kubectl boundary is explicit rather than
implicit.

## Validation

Commands actually run and confirmed passing in this environment:

```bash
gofmt -l .                                    # clean, no output
go vet ./...                                  # clean, no output
go build ./...                                # succeeds
go test ./... -count=1                        # all tests pass (handler package)
cd infra/terraform && terraform fmt -check -recursive   # clean
terraform init -backend=false && terraform validate      # "Success! The configuration is valid."
make up                                        # cluster, DB, and app deployed successfully
kubectl --context kind-config-service -n config-service get pods
make smoke-test                               # all end-to-end checks pass
```

Note: `go test ./... -race` could not be run in this environment because cgo is
not configured locally (no C toolchain); this is a local machine limitation,
not a code issue.

Live deployment was validated on a fresh `kind` cluster. Both
`config-service` and `postgres-0` reached `1/1 Running`, and the smoke test
confirmed `/ping`, `/readyz`, configuration creation and retrieval, and the
expected `404` response for an unknown configuration ID. Direct Docker Hub
access timed out in the validation environment, so the required public images
were fetched through `mirror.gcr.io`; this did not require repository changes.

## Known Limitations / Next Steps

- No incremental schema migrations (only idempotent `CREATE TABLE IF NOT
  EXISTS`) — would add `golang-migrate`/`atlas` as the service grows.
- Single PostgreSQL replica with no automated backups — fine for local use,
  not for production.
- In-memory repository fallback is a deliberate local-dev convenience but
  would be removed (fail-fast instead) in a production posture.
- No integration test against a real Postgres in `go test` (covered by the
  smoke test instead, to avoid requiring Docker-in-Docker in CI).
- No Prometheus `/metrics` endpoint yet.
